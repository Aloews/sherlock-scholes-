# Выкладка и переезд на свой домен

Коротко: **да, это делается одной кнопкой** — Actions → `deploy` → Run
workflow. Но кнопка честно делает не всё, и здесь написано, что именно она
делает, чего не делает и почему.

---

## Что где живёт сегодня

| Часть | Где | Кто выкладывает |
|---|---|---|
| Фронтенд (`dist/`) | Vercel, проект `sherlock-scholes` | **сам Vercel**, на push в `main` |
| Семь Edge-функций | Supabase, проект `konoavrduynecxblqfvq` | кнопка `deploy` |
| Схема и RPC | та же база, `supabase/migrations/*.sql` | **руками**, см. ниже |
| Расписания (pg_cron) | та же база | миграциями, значит тоже руками |
| Скраперы | GitHub Actions по расписанию | сами |

Адрес приложения зашит **в трёх местах на весь репозиторий**, и в двух из них
уже перекрывается переменной:

```
supabase/functions/tg-pay/index.ts   APP_URL       ← секрет Supabase
scripts/check-prod.mjs               PROD_APP_URL  ← переменная прогона
docs/DEPLOY_CACHING.md               пример в тексте
```

Ни одна Edge-функция не пришпилена к домену: `Access-Control-Allow-Origin` у
всех семи — `*`. Поэтому переезд **не ломает ни один вызов из приложения**.
Это проверено обходом, а не предположено; проверить самому:

```bash
node scripts/set-domain.mjs        # аудит: где сейчас записан адрес
```

## Кнопка `deploy`

Actions → **deploy** → Run workflow. Три поля:

| Поле | Что делает |
|---|---|
| `domain` | пусто — домен не трогать; `example.com` — переехать на него |
| `functions` | выложить все семь Edge-функций |
| `checks` | прогнать `tsc`, `check-i18n`, тесты и сборку **перед** выкладкой |

Порядок шагов: проверки → функции → домен → `check-prod`. Проверки идут
первыми намеренно: выложить и потом узнать — это уже не проверка, а вскрытие.

### Чего кнопка НЕ делает, и почему

**Миграции базы.** Файлы в `supabase/migrations/` названы по смыслу
(`club_room.sql`), а не отметкой времени, и применяются выборочно. `supabase
db push` прогонит такой набор целиком и по алфавиту — неверный порядок на
боевой базе дороже любого удобства. Миграции применяются вручную (SQL Editor
или MCP), и это осознанный отказ, а не «пока не сделали».

**Фронтенд.** Его выкладывает сам Vercel на push в `main`. Вторая выкладка
отсюда означала бы два источника правды о том, что сейчас в проде.

## Секреты, без которых кнопка не сработает

Settings → Secrets and variables → Actions:

| Секрет | Откуда взять | Без него |
|---|---|---|
| `SUPABASE_ACCESS_TOKEN` | supabase.com/dashboard/account/tokens | шаг функций падает сразу и громко |
| `SUPABASE_PROJECT_REF` | `konoavrduynecxblqfvq` | то же |
| `VERCEL_TOKEN` | vercel.com/account/tokens | домен придётся привязать руками |
| `VERCEL_PROJECT_ID` | `prj_zPmwoDaqeK57VzUBzFxTJGMjUm65` | то же |
| `VERCEL_TEAM_ID` | `team_e1o23XoY7tj0C19a4zwqDMhT` | то же |
| `TELEGRAM_BOT_TOKEN` | @BotFather | кнопку меню придётся переставить руками |
| `SUPABASE_ANON_KEY` | Project Settings → API → anon public | **последний шаг проверяет прод вслепую** |

Уже заведены: `SUPABASE_URL`, `SUPABASE_KEY`.

⚠️ **`SUPABASE_ANON_KEY` ЗДЕСЬ БЫЛ ЗАПИСАН КАК ЗАВЕДЁННЫЙ, А ЕГО НЕТ.** Замер
по журналу успешного прогона 20.09.2026 (блок `env` шага выкладки):

    SUPABASE_ACCESS_TOKEN  ***        SUPABASE_PROJECT_REF   ***
    VITE_SUPABASE_URL      ***        VITE_SUPABASE_ANON_KEY (пусто)

Функции выложились, а последний шаг — `check-prod` против боевых адресов —
напечатал «падений: 44», и все сорок четыре были «нет VITE_SUPABASE_* в
окружении». То есть кнопка сообщала о развале прода там, где ей просто нечем
было посмотреть. Полчаса ушло на поиск поломки, которой не было.

Сам скрипт теперь это различает: без ключей он печатает одну строку
«ПРОВЕРКА НЕ ВЫПОЛНЕНА» и выходит с кодом 2, а не выдаёт стену мнимых
падений. Но ключ всё равно нужен — иначе последний шаг кнопки бесполезен.

⚠️ **Секретов с суффиксами не заводите.** Workflow читает ровно
`secrets.SUPABASE_ACCESS_TOKEN`; `SUPABASE_ACCESS_TOKEN_2` и подобные не
читает ничто, и их наличие создаёт ложное впечатление, что ключ на месте.
Проверить, кто что читает, можно одной командой:

```bash
grep -rn "secrets\." .github/workflows/
```

⚠️ **`SUPABASE_KEY` — это service_role.** Он есть у скраперов и не нужен
выкладке; не добавляйте его туда, где он не нужен.

## Переезд на свой домен, по шагам

### 1. Купить домен

У любого регистратора. Vercel умеет продавать домены сам — тогда шаг 2
(записи DNS) отпадает, потому что домен уже в Vercel.

### 2. Нажать кнопку с доменом

Actions → `deploy` → `domain: example.com`.

Скрипт привяжет домен к проекту Vercel и **напечатает записи DNS**, которые
надо завести у регистратора, — примерно так:

```
! Vercel: домен проекта    example.com привязан, НЕ подтверждён
                           заведите у регистратора и запустите снова:
                           A @ 76.76.21.21
```

### 3. Завести записи у регистратора

⚠️ **Этого не сделает ни скрипт, ни кто-либо кроме владельца домена** — доступ
к панели регистратора есть только у него. Ради этой строки и написан весь
абзац про «одно нажатие не значит всё само».

Записи расходятся от минут до нескольких часов.

### 4. Нажать кнопку ещё раз

Тот же вызов. Теперь он:

* увидит домен подтверждённым;
* поставит секрет `APP_URL = https://example.com` (его читает `tg-pay` —
  это адрес, **куда вернуть игрока после оплаты**; пока он старый, платёж
  проходит, а человека выкидывает на старый адрес);
* переставит **кнопку меню** бота на новый адрес и **перечитает её обратно**,
  чтобы убедиться;
* сходит на `https://example.com/` и проверит, что там отвечает **само
  приложение**, а не заглушка регистратора (ищет `<div id="root">` и
  собранный `assets/*.js` — код 200 сам по себе ничего не доказывает);
* прогонит `check-prod` уже против нового адреса.

### 5. Одно действие руками: прямая ссылка

@BotFather → `/myapps` → приложение → **Edit Web App URL** → `https://example.com`

Bot API прямую ссылку (`t.me/<бот>/<имя>`) не выставляет — только BotFather.
Кнопка меню автоматизирована потому, что она и есть главный вход; про прямую
ссылку скрипт печатает напоминание и не делает вид, что справился.

## Что проверить после переезда

```bash
PROD_APP_URL=https://example.com node scripts/check-prod.mjs
node scripts/set-domain.mjs --domain=example.com   # идемпотентно
```

`check-prod` — единственная проверка, которая падает по той же причине, по
которой ломается приложение: она ходит в боевые адреса без единого мока и до
конца цепочки. Разбор — в `CLAUDE.md`.

Отдельно глазами:

* открыть бота с телефона — кнопка меню ведёт на новый адрес;
* пройти оплату Pro — после неё возвращает на новый адрес (это `APP_URL`);
* открыть прямую ссылку `t.me/<бот>/<имя>` — шаг 5 сделан.

## Откат

Старый адрес `sherlock-scholes.vercel.app` **остаётся рабочим** — Vercel не
отбирает поддомен при добавлении своего. Значит откат это:

1. `node scripts/set-domain.mjs --domain=sherlock-scholes.vercel.app`
2. BotFather → Edit Web App URL → старый адрес

Ничего не удаляется, и это главное свойство такого переезда: он обратим целиком.

## ⚠️ Про тариф Vercel, и это стоит решить до покупки домена

Проект живёт на плане **Hobby**. Свой домен там разрешён, но условия Hobby —
для личного, **некоммерческого** использования. В приложении есть `tg-pay`,
то есть приём платежей. Это вопрос к владельцу и к условиям Vercel, а не
технический: может понадобиться Pro. Лучше выяснить до переезда, чем после
первого платежа на своём домене.
