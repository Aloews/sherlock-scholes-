# Хендофф: живой футбол — события, форма, прогнозы, фэнтези

Замысел: к старту чемпионатов игрок получает актуальные события, форму
игроков, прогнозы и фэнтези-лигу.

Документ написан после осмотра кода и проверки прода. Сначала — что уже есть
и чего стоит, потом решения за заказчиком, потом фазы. **Не начинайте с кода:
две вещи ниже способны обнулить план, если решить их поздно.**

---

## 1. Что уже есть — больше, чем кажется

| Что | Где | Состояние |
|---|---|---|
| Клиент API-Football | `football_scraper/scraper/api_football.py` (190 строк) | рабочий |
| Ограничитель частоты | там же, `RateLimiter` | 10 запросов/мин |
| Дневной бюджет запросов | там же, `RequestBudget` | **100/сутки**, хранится на диске по дате UTC |
| Дисковый кэш | `scraper/cache.py` | без TTL, переезжает между прогонами CI |
| Конфиг | `football_scraper/config.json` | провайдер, лига, сезон, лимиты |

Провайдер — **API-Football v3** (`https://v3.football.api-sports.io`).

**Но:** сейчас он настроен на `league_id: 39`, `season: 2023` — исторические
данные для сборки колоды. Из живых эндпоинтов не вызывается **ни один**:
в коде есть только `players`, `teams`, `players/teams`, `leagues`.
`fixtures`, `standings`, `predictions`, `injuries`, `topscorers` не тронуты.

То есть транспорт готов, а продукта на нём нет.

---

## 2. Ограничение, которое решает всё: 100 запросов в сутки

`config.json` → `rate_limit.daily_request_budget: 100`. Это бесплатный тариф
API-Football.

Прикидка на живой продукт:

| Что | Запросов в сутки |
|---|---|
| Расписание одной лиги на неделю вперёд | 1 |
| Таблица одной лиги | 1 |
| Составы и события матча | 1–2 на матч |
| Форма игроков лиги (постранично) | 10–40 |
| Прогноз на матч (`predictions`) | 1 на матч |
| **Live-счёт опросом раз в минуту** | **до 1440** |

Одна лига в режиме «обновляем раз в сутки» укладывается в сотню. **Пять лиг
с живыми счетами — нет, и близко.** Разница между «данные вчерашние» и
«счёт меняется на глазах» — это разница между бесплатным тарифом и платным,
и это первое решение.

⚠️ **`RequestBudget` — это защита, а не лимит провайдера.** Он считает
запросы сам и упрётся в свою цифру раньше, чем провайдер. Подняв тариф, не
забудьте поднять и его, иначе всё будет молча недобирать данные.

## 3. Второе ограничение: GitHub Actions — не бэкенд для живых данных

Сейчас всё крутится ночным `daily-enrich.yml` (05:00 UTC). Для живого счёта
это не годится:

* минимальный интервал cron в GitHub Actions — 5 минут, и он **не
  гарантирован**: под нагрузкой запуски задерживаются на десятки минут;
* репозиторий уже **регулярно теряет событие `pull_request`** (см. `CLAUDE.md`)
  — на ту же инфраструктуру нельзя вешать то, что должно тикать.

**Что есть взамен, проверено на проде:** расширения `pg_cron` (1.6.4) и
`pg_net` (0.20.3) **доступны, но не установлены**. Их включение даёт
планировщик внутри Postgres с минутной гранулярностью и HTTP-вызовы прямо из
базы — этого достаточно, отдельный воркер не нужен.

Второй вариант — Supabase Edge Function по расписанию. Выбор за фазой 0.

## 4. Решения за заказчиком

Без ответов на это схему проектировать нельзя.

1. **Тариф API-Football и бюджет.** Сколько лиг, нужен ли живой счёт. От
   этого зависит и цена, и вся архитектура опроса.
2. **Какие лиги и на каком языке.** Приложение говорит на девяти языках, а
   API отдаёт названия команд и игроков на одном. Переводить имена команд
   через `card_translations`, как сделано для карточек, или показывать
   латиницей всем?
3. **«Форма игрока» — это что?** Последние N матчей, голы+ассисты, минуты,
   рейтинг провайдера? Нужна конкретная формула, иначе экран нечем наполнить.
4. **Прогнозы — чьи?** Провайдерские (`predictions` у API-Football, платный
   эндпоинт) или свои по нашим данным? Свои дешевле, но за их качество
   отвечаем мы.
5. **Фэнтези: масштаб.** См. §7 — это отдельный продукт, а не экран.
6. **Юридическое.** Прогнозы без ставок — обычно нормально; любой намёк на
   деньги, ставки или «выигрыш» меняет требования Telegram и сторов. Решить
   до, а не после.

## 5. Схема — набросок

Ориентировочно, уточнить после §4. Живые сущности **отдельно от `cards`**:
колода — это статичный контент игры, а таблица матчей меняется каждый день.

```sql
create table leagues_live (
  id            integer primary key,      -- id лиги в API-Football
  name          text not null,
  country       text,
  season        integer not null,
  active        boolean not null default true
);

create table fixtures (
  id            bigint primary key,       -- id матча в API-Football
  league_id     integer references leagues_live(id),
  kickoff_at    timestamptz not null,
  status        text not null,            -- NS / 1H / HT / 2H / FT …
  home_team     text not null,
  away_team     text not null,
  home_goals    smallint,
  away_goals    smallint,
  updated_at    timestamptz not null default now()
);
create index on fixtures (league_id, kickoff_at);

-- Форма: снапшот на дату, а не «текущее» — иначе не построить динамику
-- и нечем показать «пошёл в гору».
create table player_form (
  card_id       uuid references cards(id) on delete cascade,
  taken_on      date not null,
  matches       smallint,
  goals         smallint,
  assists       smallint,
  minutes       integer,
  rating        numeric(4,2),
  primary key (card_id, taken_on)
);
```

**Связь с колодой.** У `cards` нет идентификатора API-Football — проверено.
Чтобы показывать форму на карточке игрока, нужен `cards.api_player_id`, и
его надо чем-то заполнить: разовым сопоставлением по имени и клубу с ручной
вычиткой спорных. Это отдельная задача, и она больше, чем кажется — тёзки и
транслитерация здесь главный источник ошибок.

**RLS.** Живые таблицы — публичные на чтение, запись только из
`SECURITY DEFINER`, как в `rls_lockdown.sql`. Игрок не должен править счёт.

## 6. Фазы

Каждая мержится отдельно и сама по себе имеет смысл.

0. **Разведка.** Поднять тариф, включить `pg_cron`/`pg_net`, дёрнуть
   `fixtures` и `standings` руками, замерить реальный расход запросов.
   Ничего не строить, пока цифры не сойдутся.
1. **Расписание и результаты.** Таблица `fixtures`, ночное обновление,
   экран «сегодня/неделя». Самая маленькая фаза с видимым результатом.
2. **Таблицы лиг.** `standings`, снапшоты по датам.
3. **Форма игроков.** Требует `cards.api_player_id` (см. §5) — самая
   рискованная по данным часть.
4. **Прогнозы.** После того, как есть расписание и форма: без них прогноз
   не на чем строить и не с чем сверять.
5. **Фэнтези.** Только после 1–4. См. ниже.

## 7. Честно про фэнтези

Это **не экран, а второй продукт** внутри первого.

Сейчас Sherlock Scholes — вечеринная игра на одном телефоне: сессия на
двадцать минут, двое и больше рядом, объясняющий и угадывающие. Фэнтези —
одиночная игра на весь сезон: состав, трансферы, дедлайны, очки за тур,
лига друзей, пуши «поставь состав до субботы».

У них не совпадает **ничего**: ни длина сессии, ни число игроков, ни повод
открыть приложение. Это не аргумент против — это предупреждение, что фэнтези
потянет за собой:

* правила начисления очков и их поддержку каждый сезон;
* дедлайны и трансферные окна (а значит — надёжный планировщик, §3);
* уведомления (Telegram-бот, отдельная инфраструктура);
* модерацию названий лиг и составов;
* пересчёт очков задним числом, когда провайдер правит статистику матча —
  а он правит.

**Рекомендация:** фазы 1–4 полезны сами по себе и усиливают текущую игру —
свежая форма и события делают карточки живее. Фэнтези решать отдельно, уже
после того, как живые данные работают и видно, сколько они реально стоят в
запросах и в деньгах.

## 8. Правила проекта, которые здесь легко нарушить

* Строки — **во все девять локалей** сразу: `node scripts/check-i18n.mjs`.
  Названия команд и игроков из API приходят на одном языке — это решение §4.2,
  а не повод оставить русский в компоненте.
* `ar` — справа налево: таблицы и счёт проверить отдельно.
* Колода — **один фильтр и один предикат** (`docs/MAP.md` §3). Живые данные
  идут мимо `cards_matching`, не пытайтесь протащить их через него.
* Новая таблица — сразу RLS по образцу `rls_lockdown.sql`.
* Миграция должна быть **самодостаточной**: не рассчитывайте, что другую уже
  прогнали руками (`weekly_quests.sql` §0 — как раз о том, чем это кончается).
* Порог mutation 80 понижать нельзя.
* Одна ветка от свежего `main`; не ставить PR базой на другую ветку `claude/*`.
