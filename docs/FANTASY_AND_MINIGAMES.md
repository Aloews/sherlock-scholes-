# Фэнтези-лига и мини-игры — устройство

Проект решения, не код. Всё, что ниже, опирается на измеренные числа, а не на
предположения о том, что «наверное есть». Замеры сделаны 10 августа 2026 по
боевой базе; команды для повторной проверки — в конце.

---

## 1. Главное ограничение, и почему оно определяет всё

**Постатейной статистики игроков у нас нет и не появится бесплатно.**

Классическое фэнтези (Fantasy Premier League и подобные) начисляет очки за
события в матче: гол, пас, сухарь, жёлтая. Ничего этого в данных нет.
`the-odds-api` отдаёт расписание и счёт — и всё. `cards.career_stats` хранит
матчи и голы **за карьеру**, из Википедии, обновляется раз в сутки: это
история, а не события конкретного тура.

Отсюда развилка, и её надо сделать осознанно:

| Путь | Что даёт | Чего стоит |
|---|---|---|
| **A. Фэнтези по клубам** | работает на сегодняшних данных, ноль новых источников | очки грубее: за результат клуба, не за действия игрока |
| **B. Классическое фэнтези** | голы, пасы, сухари | новый платный провайдер статистики; отдельный конвейер, свой бюджет |

Ниже подробно расписан путь **A**, потому что он собирается из трёх уже
работающих систем. Путь B он не закрывает: когда появится провайдер, схема
ниже принимает его как второй источник очков, не переделываясь.

---

## 2. Почему путь A вообще возможен — числа

Связь «карточка игрока → реальный матч» уже существует, просто ею никто не
пользовался. Она идёт через `card_current_club` (клуб, который игрок не
покидал на момент последнего чтения статьи; пересобирается ночью через
pg_cron) и `club_match_key()` — ту же функцию, которой сопоставляются составы.

| Что | Сколько |
|---|---|
| карточек игроков, активных | 2919 |
| из них с текущим клубом | 1164 |
| **из них с клубом, у которого есть ближайший матч** | **790** |
| клубов, сошедшихся с расписанием | 117 |
| ближайших матчей, где есть хоть одна наша карточка | 114 из 218 |

790 игроков и 114 матчей — это достаточная глубина, чтобы состав из 5–8
человек собирался осмысленно, а не из того, что осталось.

**Чего эти числа не говорят:** 1164 из 2919 — это меньше половины карточек с
клубом, и «текущий» здесь означает «не ушёл к моменту последнего чтения
статьи». Состав может отставать от трансфера на сутки и более. Экран обязан
писать «состав на дату», как это уже делает `deck_squads` — иначе мы выдаём
устаревший факт за свежий, а это ровно то, за что раньше выкинули Википедию
как источник счёта.

## 3. Схема

Три таблицы. Ни одной новой сущности сверх необходимого: лиги — это `friendships`
плюс имя, туры — это неделя.

```sql
-- Тур. Одна строка на неделю; окно закрывается первым стартовым свистком.
fantasy_round (
  id            bigserial primary key,
  starts_at     timestamptz not null,   -- начало приёма составов
  locks_at      timestamptz not null,   -- первый матч тура: составы заморожены
  ends_at       timestamptz not null,
  settled_at    timestamptz
)

-- Состав игрока на тур. Ровно SQUAD_SIZE строк, проверяется в RPC.
fantasy_pick (
  round_id      bigint not null references fantasy_round(id) on delete cascade,
  player_id     bigint not null references players(id)       on delete cascade,
  card_id       uuid   not null references cards(id)         on delete cascade,
  is_captain    boolean not null default false,
  primary key (round_id, player_id, card_id)
)

-- Приватная лига. Владелец + участники; приглашение переиспользует room_invites-подход.
fantasy_league (
  id            bigserial primary key,
  owner_id      bigint not null references players(id) on delete cascade,
  name          text   not null,
  join_code     char(6) not null unique
)
fantasy_league_member (league_id, player_id, primary key (league_id, player_id))
```

Очки за тур **не хранятся отдельной колонкой у состава**, а считаются
функцией из `fixtures` и `card_current_club`. Причина та же, по которой
`cards_matching` один: два места, считающие одно и то же число, рано или
поздно разойдутся, и разойдутся молча.

---

## 4. Как начисляются очки (путь A)

За каждую карточку в составе, за каждый матч её клуба внутри тура:

| Событие | Очки |
|---|---|
| клуб выиграл | 3 |
| ничья | 1 |
| клуб не пропустил | +2 |
| за каждый забитый клубом гол | +1 |
| поражение с разницей 3+ | −1 |
| капитан | ×2 |

Правило живёт в `IMMUTABLE`-функции, как `prediction_points` — чтобы его можно
было протестировать отдельно и показать игроку, не пересказывая `UPDATE`.

**Честная слабость:** все игроки одного клуба получают одинаково. Вратарь и
нападающий «Барселоны» неразличимы. Смягчается позицией из `cards.position`
(сухарь ценнее защитникам, голы — нападающим), но не лечится — это цена пути A,
и её надо назвать игроку прямо в правилах, а не обнаружить постфактум.

## 5. Что переиспользуется, а не пишется заново

| Нужно | Уже есть |
|---|---|
| кто с кем играет | `friendships`, `player_encounters` |
| пригласить в лигу | `room_invites` — та же форма: приглашение, TTL, один тап |
| расписание и счёт | `fixtures`, `upsert_fixture_scores`, действие `scores` |
| состав клуба | `card_current_club`, пересборка ночью в pg_cron |
| закрытие по свистку | `predict_match` — там уже сравнение с `now()` на сервере |
| очки и профиль | `increment_player_stats`, XP |

Новый код — три таблицы, четыре RPC и один экран. Всё остальное уже работает.

---

## 6. Порядок, в котором это стоит делать

1. **Очки за тур как функция** — без UI. Проверяется SQL-запросом на прошлых
   матчах: правило можно оценить до того, как под него нарисован экран.
2. **Состав и тур** — сборка состава, заморозка по `locks_at`, таблица за тур.
3. **Лиги друзей** — поверх готового: список — это `order by` по очкам тура.
4. **Провайдер статистики (путь B)** — только когда первые три живут и на них
   смотрят. Тогда `fantasy_pick` не меняется, добавляется второй источник очков.

## 7. Мини-игры

Кандидаты, отсортированные по тому, сколько нового кода требуют. Первые три
не требуют **никаких** новых данных.

| Игра | Из чего | Новый источник |
|---|---|---|
| **Кто известнее** — две карточки, угадай более известную | ✅ сделано — `cards.fame` (не сырые `pageviews`: разные семьи живут на разных шкалах, см. `deck_fame.sql`), `whos_more_famous.sql`, `/famous` | нет |
| **Чей состав** — 5 игроков клуба, угадай клуб | ✅ сделано — `card_current_club`/`deck_squads(5)` (72 состава), `whose_squad.sql`, `/squad` | нет |
| **Угадай счёт** | уже сделано — `match_predictions` | нет |
| **Карьерная лестница** — клубы по годам, угадай игрока | `cards.career_stats` | нет |
| **Гол или нет** — по завершённым матчам | `fixtures` со счётом | нет, но регулярный `scores` уже есть (`schedule_fetch_fixtures.sql`, #100) |

«Кто известнее» открыла раздел мини-игр, как и планировалось здесь — самая
дешёвая из всех, одна RPC и один экран поверх уже проиндексированных данных.
«Чей состав» — вторая по тому же принципу: имена вместо фамилий (см.
шапку `whose_squad.sql` — фамилию из полного имени надёжно не вырезать,
бразильские карточки играют под именем), клуб-ответ и три отвлекающих
берутся из `deck_squads(5)` полностью случайно, без выравнивания по
узнаваемости — та же честная слабость v1, что и у «Кто известнее».

## 8. Проверить числа заново

```sql
-- Сколько карточек игроков привязано к клубу с ближайшим матчем
with f as (
  select public.club_match_key(home_team) hk, public.club_match_key(away_team) ak
  from fixtures where commence_at > now()
)
select count(distinct cc.card_id)
from card_current_club cc join f on cc.club_key in (f.hk, f.ak);
```

Если это число заметно упало — сначала смотреть `rebuild_card_current_clubs()`
и ночной cron, а не схему фэнтези: связь держится на составах, а они
пересобираются каждую ночь.
