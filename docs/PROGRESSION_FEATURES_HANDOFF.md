## 1. Что решить до кодинга

Задай эти вопросы заказчику — от ответов зависит вся схема.

1. **Рейтинг: по чему считаем?** Суммарные очки за всё время (`player_stats.
   total_score` уже есть) или сезонный/недельный? Сезонный требует таблицу
   периодов и снапшоты. Дельта (▲/▼) в макете подразумевает сравнение с
   предыдущим срезом — значит снапшоты обязательны.
2. **«Друзья» в фильтре рейтинга** — откуда брать список? В Telegram Mini App
   нет API списка друзей. Варианты: те, с кем играл в одной комнате
   (`room_players`), или выкинуть фильтр.
3. **Уровень: формула.** Например `level = floor(sqrt(xp / 100)) + 1`. Что даёт
   XP — угаданная карта, победа, выполненное задание? Нужны конкретные числа.
4. **Звания** («Детектив-инспектор» в макете) — просто подпись по уровню, или
   отдельная сущность? Проще: массив названий по уровням в коде + i18n.
5. **Задания**: фиксированный набор на каждый день для всех, или персональные?
   Ротация случайная или по расписанию? Награда — только XP или ещё что-то?
6. **Серия (streak)**: считается по дням с любой сыгранной игрой или по
   выполненным заданиям? Что её обрывает и в каком часовом поясе — UTC или
   локальное время игрока?
7. **Достижения**: список и условия. Их надо выписать явно, иначе экран нечем
   наполнить.

## 3. Что нужно завести

### 3.1. Схема

Ориентировочно (уточнить после §1):

```sql
-- Опыт и уровень. Уровень выводится из xp, не хранится отдельно.
alter table player_stats add column xp integer not null default 0;

-- Достижения: справочник + факт получения.
create table achievements (
  code        text primary key,          -- 'first_win', 'cards_100', …
  icon        text not null,             -- имя иконки @tabler/icons-react
  sort_order  integer not null default 0
);
create table player_achievements (
  player_id   bigint references players(id) on delete cascade,
  code        text   references achievements(code),
  unlocked_at timestamptz not null default now(),
  primary key (player_id, code)
);

-- Ежедневные задания: справочник, назначение на дату, прогресс.
create table daily_tasks (
  code       text primary key,
  target     integer not null,
  reward_xp  integer not null
);
create table player_daily_tasks (
  player_id  bigint references players(id) on delete cascade,
  task_code  text   references daily_tasks(code),
  day        date   not null,
  progress   integer not null default 0,
  claimed_at timestamptz,
  primary key (player_id, task_code, day)
);

-- Серия дней.
alter table player_stats add column streak_days integer not null default 0;
alter table player_stats add column streak_last_day date;

-- Снапшоты рейтинга — только если нужна дельта (см. §1.1).
create table leaderboard_snapshots (
  player_id bigint references players(id) on delete cascade,
  taken_on  date not null,
  score     integer not null,
  rank      integer not null,
  primary key (player_id, taken_on)
);
```

**Названия достижений и заданий — в i18n, не в БД.** В таблице только `code`;
подпись берётся из локали по ключу вроде `achievements.first_win`. Иначе
придётся переводить содержимое БД, а в приложении девять языков.

### 3.2. RLS

В репозитории есть `supabase/migrations/rls_lockdown.sql` — посмотрите, как
закрыты существующие таблицы, и закройте новые так же. Игрок должен читать
свой прогресс и общий лидерборд, но **не** уметь писать себе XP и отмечать
задания выполненными. Начисление — только через RPC с `security definer`,
как сделано в других местах проекта.

### 3.3. Начисление

Прогресс должен считаться **на сервере**, в момент завершения игры/раунда.
Клиентский инкремент подделывается тривиально. Смотрите существующие RPC в
`supabase/migrations/` как образец стиля.

## 4. Экраны

Все три уже нарисованы в прототипе; токены и правила — `docs/DESIGN_SYSTEM.md`.

- **Рейтинг** (`isRating`): сегмент-контрол фильтров + строки лидерборда —
  ранг, инициалы в скруглённом квадрате, имя, очки, дельта.
- **Профиль** (`isProfile`): аватар 64px, уровень и звание, полоса прогресса до
  следующего уровня, три стата, горизонтальная лента достижений
  (заблокированные — с пониженной непрозрачностью), список настроек.
- **Задания дня** (`isDaily`): полоса из семи дней серии, карточки заданий с
  прогресс-баром и кнопкой «Забрать награду» у выполненных.

Точные размеры и цвета — в разметке прототипа; **не копируйте инлайн-стили**,
переписывайте на Tailwind по конвенциям репозитория.

### Куда это встраивается

Эти экраны — недостающие вкладки нижнего таб-бара из макета (Рейтинг,
Профиль). Если таб-бар к этому моменту уже сделан, добавьте вкладки туда;
если нет — см. `docs/DESIGN_V2_HANDOFF.md` §4.

## 5. Фазы

Каждая мержится отдельно.

1. **Уровни и XP.** Колонка `xp`, формула уровня, начисление, полоса прогресса
   в профиле. Самая маленькая фаза, даёт видимый результат.
2. **Достижения.** Справочник, разблокировка, лента в профиле.
3. **Рейтинг.** Лидерборд без дельты; дельта — отдельным шагом со снапшотами.
4. **Задания и серия.** Самая крупная: ротация, прогресс, награды, обрыв серии.

---

## 6. Правила

- **Ничего не начислять на клиенте.** Только RPC.
- **i18n во все девять локалей** (`src/shared/i18n/locales/`).
- **Цвета только через токены** дизайн-системы; исключения — цвета-данные,
  см. `docs/DESIGN_SYSTEM.md`.
- **Оба дизайна.** Новые экраны должны выглядеть осмысленно и в `master`, и в
  `classic` — как минимум через общие токены.
- Миграции класть в `supabase/migrations/`, следуя именованию соседних файлов.
- `npm run typecheck` и `npm run build` должны проходить.
- Рецепт визуальной проверки — `docs/DESIGN_V2_HANDOFF.md` §7.
