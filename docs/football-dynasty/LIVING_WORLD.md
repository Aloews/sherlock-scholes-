# Living World Simulation

## Goal
A persistent, systemic world in which the player can observe events, choose how to respond, and have the world react to that response. Events are not isolated dialogue cards: their consequences must be recorded and influence future simulation.

## Event loop
1. **World tick**: advance time and update actors, locations, relationships, pressure, schedules, and active situations.
2. **Event detection**: create situations from world-state predicates (not only random rolls). Examples: local crime, news coverage, a rival's public move, club incident, weather disruption, a player spotted at a venue.
3. **Player awareness**: event reaches the player only through plausible channels (direct observation, NPC conversation, news, phone, social feed, club staff).
4. **Player response**: choices, movement, dialogue, intervention, ignoring, delayed response, or an action that conflicts with the event.
5. **Resolution**: action is validated against time, location, inventory, resources, relationships, and prior state; no choice is a cosmetic button.
6. **World reaction**: affected NPCs/factions/media/club staff respond using their knowledge, motives, trust, fear, resources, and relationships.
7. **Persistence**: store world facts, causal links, actor knowledge, response, outcome and follow-up triggers. Later ticks can revisit unresolved threads or generate second-order events.

## Systemic event contract
Each event should have a stable ID, type/category, seed, created timestamp/game time, location, involved actor IDs, visibility channels, urgency, expiry/decay policy, state (generated/known/active/resolved/expired), eligible responses, prerequisite facts, outcome facts, and causal parent event IDs. Avoid event spam: deduplicate by event key, cooldown, actor/location eligibility and active-event caps. Generated events must be deterministic under the same seed and input world snapshot.

## NPC/world model
Persist a compact actor state: identity/role, current location and schedule, goals, traits, relationships to player and relevant actors, inventory/resources where useful, awareness/knowledge facts, last actions, and bounded memory summaries. NPC decisions should use a shared constrained action set and the same world rules as player actions. Do not let NPCs react to facts they could not have learned.

## Response mechanics
Player choices should resolve into actions, not direct outcome flags. Action outcomes can include success/failure/partial success, cost, witnesses, evidence, time elapsed, new knowledge and updated relationship/heat/reputation. A response may be ignored, delayed, hidden, publicly visible, or misinterpreted. World reaction must derive from those outcomes and who knows about them.

## Consequence propagation
Use append-only causal facts and a bounded reaction queue. A reaction records its trigger fact, eligible observers/actors, delay, attempted action and outcome. Reactions may spawn events, change schedules/locations/relationships, alter access or prices, influence media coverage, create investigation pressure, and affect later choices. Enforce caps on reactions per tick, depth and lifespan to prevent infinite cascades. Provide a way to inspect the causal chain in tests/dev tools.

## Initial vertical slice (acceptance target)
- A location-based incident can be generated by a deterministic world tick and is delivered via an appropriate channel (e.g. local news).
- Player may intervene, report, investigate, leave, or ignore it; actions require correct location/time/state and produce auditable outcomes.
- NPC witnesses/media/police or affected parties react only if they have knowledge and relevant motives.
- At least one second-order reaction is triggered by the player's action and changes later world state/event eligibility (e.g. witnesses report intervention, media follows up, a contact relationship shifts, or an investigation opens).
- Reloading the campaign preserves the event state, response, causal links and queued reactions; duplicate commands are idempotent.
- Tests cover deterministic replay, invalid action rejection, hidden knowledge, reaction caps, cascade termination, expiry, and persistence/reload.

## Implementation phases
- **LW0 – Contracts/data model:** typed event, actor knowledge, action, outcome, world fact, causal link and reaction queue; schema and migration parity.
- **LW1 – World tick/event generation:** deterministic predicates plus seeded variation, schedules/locations, event cooldown/deduplication.
- **LW2 – Awareness delivery:** channel rules and actor knowledge; events are not globally visible.
- **LW3 – Player actions:** action validation, costs, witnesses, partial/failure outcomes, idempotency.
- **LW4 – NPC response:** knowledge-gated, motive-based decisions with shared action constraints.
- **LW5 – Consequence graph:** bounded delayed reactions, second-order effects, persistent facts.
- **LW6 – UI integration:** event feed, response interaction and visible state changes; no tutorial/explanatory captions in production UI.
- **LW7 – Validation/calibration:** replay tests, DB integration, RLS, migration parity, workload/loop guards, CI and acceptance walkthrough.

The screenshot is a design reference for emergent consequences and believable world continuity, not a claim that Rockstar's proprietary implementation is known or copied. Start with a small, testable incident chain; grow the actor and event systems from evidence, not from a sprawling collection of scripted quests.
