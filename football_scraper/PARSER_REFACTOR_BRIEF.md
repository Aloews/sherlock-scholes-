# football_scraper/run.py — ревизия и переработка

Этот документ — бриф для отдельной (новой) рабочей сессии Claude Code,
чья единственная задача — привести `run.py` в порядок: проверить,
исправить баги и переработать структуру, не сломав ничего из того, чем
реально пользуется Евгений (человек без технического бэкграунда, видит
только `.bat`-файлы).

Не путать с игровым фронтендом/Mini App — это отдельный офлайн-инструмент,
запускается вручную, в прод Mini App не входит (см. `CONTEXT.md`).

## 1. Диагноз: почему парсер стал неудобным

`run.py` — **3649 строк / 168 КБ**, при этом рядом уже существует пакет
`scraper/` (2928 строк: `api_football.py`, `cache.py`, `config.py`,
`dedup.py`, `history.py`, `pageviews.py`, `pipeline.py`,
`supabase_writer.py`, `team_filter.py`, `wikidata.py`) с приличными,
переиспользуемыми модулями.

Проблема в том, что **новые фичи НЕ уходили в `scraper/`, а копипастились
прямо в `run.py`** как новые функции верхнего уровня. Список команд,
каждая — отдельная функция в `run.py`, каждая добавляла свой флаг в
`main()`:

```
run_pageviews            run_cards_pageviews      run_photos
run_cards_photos         run_cards_name_en        run_cards_translations
run_cards_country        run_cards_position       run_cards_legend_career
run_collect_history      run_to_cards             run_find_dups
```

Плюс к каждой команде — собственные локальные хелперы прямо в `run.py`
(а не в `scraper/wikidata.py`, где им место), например:
`search_close_titles`, `resolve_card_qid`, `cards_photos_candidates`,
`cards_photos_en_candidates`, `cards_photos_props`,
`_search_qualifier_ok` — это один и тот же патторн «найти статью ruwiki
по названию карточки → достать QID → сходить в Wikidata → записать
PATCH-ом», переизобретённый заново для photos, name_en, translations,
country, position, legend_career отдельно, с небольшими вариациями.

Следствия:
- **Дублирование логики** резолвинга ruwiki/QID в 5-6 местах с мелкими
  расхождениями — почва для несогласованных багов (одна команда находит
  статью, другая с тем же именем — нет).
- **`main()`** — гигантский `argparse` с ~15 булевыми флагами в одном
  файле (строки 3235-3648), без подкоманд, без общей диспетчеризации.
- **Ноль тестов на уровне `run.py`.** В `tests/` есть тесты только для
  `scraper/*` модулей (`test_dedup.py`, `test_merge.py`,
  `test_pageviews.py`, `test_team_filter.py`, `test_descriptions.py`).
  Ни одна из ~12 `run_*`-команд не покрыта тестом — значит, любой
  рефактор сейчас идёт вслепую.
- Каждая команда сама печатает свой dry-run «план» (`print_plan`,
  `print_pageviews_plan`, `print_to_cards_plan`, и т.д.) — тоже
  дублирование одного и того же по форме отчёта.

## 2. Что трогать нельзя (жёсткие ограничения)

1. **Внешнее поведение всех текущих флагов не должно измениться.**
   `.bat`-файлы (`sbor_seria_a.bat`, `sbor_la_liga.bat`,
   `sbor_bundesliga.bat`, `sbor_ligue1.bat`, `sbor_prosmotry.bat`,
   `poisk_dublei.bat`) вызывают `run.py` с конкретными флагами и это
   единственный интерфейс, которым пользуется нетехнический человек
   (см. `MANUAL.md`). Любое изменение имени флага/поведения — это
   поломка прод-инструмента.
2. **Safety-механизмы обязательны и не подлежат ослаблению:** пауза
   между запросами (`min_pause_seconds`), дневной бюджет запросов
   (`daily_request_budget`), retry с backoff на 429/5xx, дисковый кэш
   (чтобы dry-run не тратил бюджет дважды), idempotent UPSERT/PATCH
   (guard `IS NULL` там, где он есть).
3. **Бизнес-правила из `CONTEXT.md` неприкосновенны без явного
   согласия:** сезон 2023 без динамики, порог pageviews > 3000, фаззи-
   дедуп по `canonical_key`, name-quality guard (не перезаписывать
   хороший `name_ru` худшим).
4. Никаких новых внешних зависимостей без необходимости; стиль кода —
   как в существующем `scraper/` (простой процедурный Python, без
   лишних абстракций/классов там, где хватает функций).
5. Рефактор — **пошаговый и проверяемый**, не «переписать всё с нуля
   одним PR». Каждый шаг — один перенесённый/исправленный кусок +
   прогон существующих `tests/` + там, где можно, offline-сравнение
   поведения до/после.

## 3. Цель переработки

`run.py` должен стать **тонким CLI-роутером**: парсит аргументы,
вызывает функцию из `scraper/`, печатает результат. Вся бизнес-логика
команд переезжает в `scraper/` как отдельные, тестируемые модули —
по аналогии с тем, как уже сделаны `scraper/history.py` и
`scraper/pageviews.py` (туда `run.py` просто зовёт
`run_collect_history(...)` / импортированные хелперы pageviews).

Конкретно:
- Единый переиспользуемый **резолвер карточка → ruwiki/enwiki статья →
  QID** (сейчас размазан по `resolve_card_qid`, `cards_photos_*`,
  `cards_photos_en_candidates`, `_search_qualifier_ok` в `run.py`) —
  вынести в `scraper/wikidata.py` (или новый `scraper/card_resolver.py`)
  и переиспользовать в photos/name_en/translations/country/position/
  legend_career вместо 6 похожих копий.
- Единый **dry-run report helper** вместо `print_plan` /
  `print_pageviews_plan` / `print_to_cards_plan` и т.п.
- Каждая `run_*`-команда переезжает в `scraper/commands/<name>.py` (или
  подходящий существующий модуль), `run.py` оставляет только вызов.
- `main()` — либо `argparse` с subparsers (`run.py cards photos`,
  `run.py cards name-en`, ...) с сохранением **старых флагов как
  алиасов** (чтобы `.bat`-файлы не трогать), либо явная dict-диспетчеризация
  `{flag: handler}` — на усмотрение исполнителя, лишь бы `main()`
  перестал быть простынёй на 400 строк.

## 4. План работы для новой сессии

1. **Инвентаризация.** Составить таблицу всех `run_*` команд: что
   уникально, что общее (резолвер, dry-run print, budget/cache wiring).
   Не менять код на этом шаге.
2. **Страховка перед рефактором.** Там, где нет тестов — написать
   минимальные offline/characterization-тесты (на фикстурах, без сети)
   для хотя бы дедуп-чувствительных и часто дёргаемых команд
   (`--to-cards`, `--find-dups`, резолвер QID), чтобы рефактор было чем
   проверить. Использовать существующий стиль из `tests/test_dedup.py`.
3. **Вынести общий резолвер** ruwiki/QID в `scraper/`, переключить на
   него команды по одной, каждый раз прогоняя тесты + `--dry-run`
   сравнение отчёта до/после на реальных (закэшированных) данных, если
   возможно.
4. **Перенести оставшиеся команды** в `scraper/` по одной, с коммитом на
   каждую (маленькие обозримые диффы, не один гигантский коммит).
5. **Разгрузить `main()`** до тонкого роутера в последнюю очередь, когда
   вся логика уже вынесена.
6. **Актуализировать `README.md`/`MANUAL.md`/`CONTEXT.md`**, если
   изменилось расположение кода (пользовательские команды/`.bat`-файлы
   не меняются, значит `MANUAL.md`, скорее всего, трогать не придётся —
   проверить).

## 5. Критерии готовности

- [ ] `run.py` радикально короче (ориентир: на порядок меньше, а не
      минус 10%), без скопированной бизнес-логики команд.
- [ ] Резолвер ruwiki/QID существует в одном месте и используется всеми
      cards-командами.
- [ ] Каждая перенесённая команда имеет хотя бы один offline-тест.
- [ ] Все существующие флаги (`--dry-run`, `--pageviews`, `--to-cards`,
      `--cards-pageviews`, `--photos`, `--cards-photos`,
      `--cards-name-en`, `--cards-translations`, `--cards-country`,
      `--cards-legend-career`, `--collect-history`, `--refresh-history`,
      `--history-budget`, `--history-limit`, `--cards-position`,
      `--langs`, `--redo-translit`, `--find-dups`) работают как раньше —
      проверено хотя бы через `--dry-run` на каждый.
- [ ] Все 6 `.bat`-файлов по-прежнему работают без изменений в них
      самих.
- [ ] `python3 -m tests.test_*` (весь `tests/`) проходит.
- [ ] Найденные по пути баги — задокументированы отдельным списком в
      PR/коммитах (что было не так, как исправлено), а не молча
      подмешаны в рефактор.

## 6. Формат работы

- Маленькие коммиты, один логический шаг — один коммит.
- Перед каждым риском (реальная запись в Supabase, трата API-бюджета) —
  сверяться с `--dry-run`, но не гонять его без нужды (тратит
  Wikimedia/API-Football бюджет — см. `CONTEXT.md` «ПРАВИЛА РАБОТЫ»).
- Если непонятно, ломает ли изменение реальное поведение — сначала
  спросить/остановиться, не гадать.
